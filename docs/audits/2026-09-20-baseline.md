# Interview Integrity Monitor — Code Review and Audit

Reviewed: 20 September 2026. Input: the supplied `interview-integrity-monitor.zip`.

**Verdict: retain as a developer prototype. Do not deploy this version for real interviews until the device-lifecycle and evidence-retention defects are fixed.** The architecture has useful safeguards, but passing unit tests does not establish native-device reliability or detection accuracy.

This review inspected the Python worker, JavaScript dashboard and companion, audit signing and reporting, optional cloud API, Rust/Tauri shell, packaging scripts, tests and documentation. No application fixes were applied. Builds and tests ran against an extracted review copy; the uploaded archive was not modified.

## F01 — Pre-flight devices can outlive the visible check

**Location:** `web/app.js`, lines 110–161, particularly the asynchronous acquisition at 117 and cleanup at 151–157.

`startPreflight()` awaits `getUserMedia()` and then unconditionally stores the stream and attaches it to the video element. If the user closes the dialog while the permission request is pending, `stopPreflight()` sees no stream to stop. When permission subsequently resolves, acquisition continues although the dialog is closed.

**Reproduction:** execute the actual dashboard script in Node's VM with a minimal DOM and a deferred `getUserMedia` promise. Start pre-flight, close it, then resolve permission with mocked video/audio tracks. Result: `dialogOpen=false`, `tracksStopped=0`, `hiddenVideoHasStream=true`.

**Impact:** devices can remain active without the visible check. The session's “Stop monitoring” handler only stops the Python worker; it does not clean up this separately acquired browser stream. This is a lifecycle/privacy defect, not evidence of saved or transmitted audio/video. Physical devices were not exercised.

**Fix:** use a request-generation token or explicit cancelled state. After permission resolves, immediately stop every track if the request is obsolete or the dialog has closed. Invalidate pending acquisition during cleanup. Keep each request's stream local until accepted. Include acquisition errors, repeated open/close, navigation, and session-stop behavior in lifecycle tests.

**Acceptance check:** close while permission is pending, then grant permission; every returned track must immediately become stopped and the video must have no stream.

## F02 — Stop is serialized behind unbounded native work

**Location:** `worker/engine.py`, `poll()` at 72–113, `heartbeat()` at 66–70 and `stop()` at 136–147; native collectors in `worker/native.py`.

`poll()` holds the engine's shared `RLock` while calling each detector's `scan()`. Stop and heartbeat use the same lock. The timeout checks happen before scanning, so a native API that stalls after those checks can prevent subsequent timeout enforcement and cleanup. Running `poll()` through `asyncio.to_thread()` does not make the underlying scan cancellable.

**Reproduction:** block a fake detector on a thread event, request stop on another thread, and observe that stop cannot complete and `active` stays true. Releasing the detector allows stop to finish. The test established the lock dependency, not the frequency of real OS hangs.

**Impact:** the visible stop control and 15-second heartbeat expiry cannot guarantee bounded shutdown. A camera subprocess already started on a previous poll may remain active while another probe stalls.

**Fix:** keep state locks short; execute probes outside the lock with a session-generation check before committing results. Isolate potentially blocking native work in killable processes or another mechanism with enforceable deadlines. Maintain an independent device-shutdown path. A thread timeout alone cannot terminate a stuck native call.

**Acceptance check:** a deliberately never-returning probe must not prevent stop, camera cleanup, or watchdog expiry within the documented deadline.

## F03 — A signed report can omit evidence the dashboard observed

**Location:** `worker/engine.py`, lines 101–112; `worker/report.py`, lines 88–94 and 135–147.

Windows/gaze detectors may scan every two seconds, while full result snapshots are saved every ten seconds. A newly detected signal immediately stores only a timeline title and explanation. Its structured evidence, confidence, limitation and detector identity are saved only if it survives until a full sample. The PDF builds its detailed observations and observation count exclusively from those full samples.

**Reproduction:** at simulated t=100, return no signal; at t=102, return a transient overlay with unique evidence; at t=104, return no signal and stop. The dashboard snapshot contained one signal. The exported bundle passed signature verification but contained zero structured signals. The title survived in the timeline; the unique evidence did not.

**Impact:** the report may count zero observations and state that no matching observations were retained in samples, despite a timeline entry showing that one occurred. The signature protects stored bytes; it cannot recover omitted evidence.

**Fix:** append the full minimized signal on first observation, including its ID, detector, evidence, limitations and timestamp; separately record resolution. Build report observations from those signed signal events. Preserve periodic samples for coverage and trends.

**Acceptance check:** any signal appearing in a visible dashboard update must have corresponding structured, signed evidence in the final export even if it lasts less than ten seconds.

## F04 — Legitimate extension inventories are rejected as modified

**Location:** `companion/popup.js`, lines 12–16; `worker/engine.py`, lines 162–170.

The companion sorts names using locale-sensitive `localeCompare()` and serializes with `JSON.stringify()`. Python sorts by Unicode code point and uses `json.dumps()` with its default ASCII escaping. These are different byte representations.

**Reproductions:** a single enabled extension named `é`, and two enabled extensions named `a` and `Z`. Both companion-equivalent digests were rejected by the actual worker with “unauthenticated modifications detected.” The Unicode example fails regardless of multi-item sort order.

**Impact:** ordinary international or mixed-case inventories can fail import and receive a misleading tampering error. Existing digest tests generate the expected checksum in Python, so they miss the cross-language boundary.

**Fix:** specify a versioned canonical byte format and identical sort/truncation rules in both implementations; include non-ASCII, mixed-case, emoji and long-name fixtures generated by the real companion. A checksum supplied with editable content establishes byte consistency, not browser attestation or authenticity; labels should say so.

## F05 — Privacy disclosures have drifted from implementation

**Location:** `web/index.html`, lines 22, 47 and 120; `web/app.js`, lines 110–161; `worker/gaze.py`, lines 95–101 and 139–148; `docs/security.md`, opening privacy description.

Three related discrepancies need correction:

- The synthetic demo says it is not monitoring the device, and the README says it never opens devices. Pre-flight remains enabled in demo and invokes real `getUserMedia({video:true,audio:true})`. A mocked run confirmed a device request in `?demo=1`. This still requires the user's pre-flight action and browser permission; it is not a permission bypass.
- The privacy panel says no audio is collected, and the security document says no audio streams are opened. Pre-flight opens and processes a microphone stream locally. “Not recorded” is narrower and can remain true; “not opened/collected” does not describe the current flow.
- The camera disclosure says only eye-position aggregates are retained. The detector also emits `faces_count`, `secondary_person`, lighting metrics and multiple-face observations, which the worker can persist in signed samples/timeline events.

**Fix:** make demo hardware-free; explicitly disclose optional local microphone preview; update and version camera consent to cover face-count observations and retained metrics, or remove the undisclosed data. Align the UI, README, security document and generated report with one reviewed data inventory.

## F06 — Summary output is partly mock behavior and contains factual errors

**Location:** `worker/prompt_loop.py`, lines 49–52, 61–71, 119–131, 199–205 and 222–229; `worker/report.py`, lines 101–110.

The default provider is `MockLLMProvider`, so the shipped path has no real LLM integration. It returns a canned sentence or eventually a deterministic fallback. The fallback counts every `True` field in consent, including `accepted`, as an enabled monitoring scope. With only processes enabled, the reproduced summary reports “2 enabled technical scopes (accepted, processes).”

Additionally, `PromptLoopConfig.passing_score` and `strict_compliance` do not control the acceptance branch. Configuring a passing score of 1.0 still accepted a draft scored 0.85. The fallback also reports a fixed 0.7 score without evaluating the fallback text.

**Impact:** a generated report can misstate what was monitored and display a “Compliance score” that is not a reliable measure of factual correctness or compliance. Existing tests cover scripted drafts, not all production defaults.

**Fix:** filter consent through the engine's actual scope list; enforce configured thresholds or remove unsupported options; use a clearly labelled deterministic summary until a real provider is intentionally integrated. Replace “Compliance score” with an accurately scoped label or omit it. Do not add external data transfer without a separate design and consent review.

## F07 — No deadline for the camera's first result

**Location:** `worker/gaze.py`, lines 114–137.

`last_update` starts at zero and the stale-data check is conditional on it being truthy. If the subprocess stays alive but blocks opening the camera or reading its first frame, no startup deadline applies. It remains `partial` with calibration status indefinitely. This was reproduced with a live, silent mocked subprocess.

**Fix:** record startup time; use separate startup and subsequent-measurement deadlines; terminate/release a stalled camera worker and show an explicit unavailable/retry state. Do not count a process that has returned no measurements as a detector returning data.

## F08 — Browser test contains a stale assertion

**Location:** `tests/browser.mjs`, line 41; `worker/detectors.py`, `ProcessDetector.scan()` result detail.

The test waits for `Executable names only`. The production string is `Executable names and binary metadata; no paths or arguments retained.` That substring cannot match, so a healthy process-only workflow will time out at this assertion before reaching export checks.

**Fix:** assert structured detector status or stable test identifiers instead of presentation copy, and run the complete browser flow. Real Chromium execution was unavailable during this audit; this finding follows directly from the two strings.

## F09 — Published source checksums do not describe this archive

**Location:** `SOURCE-SHA256.txt` and the corresponding archive members.

Recomputing every listed SHA-256 yielded 37 matches and 21 mismatches, with no missing listed files. Mismatches include the worker, dashboard, companion, tests, package configuration and sample reports. This establishes a stale manifest; it does not by itself establish malicious modification.

**Fix:** generate the manifest from a clean release staging directory after all edits and sample generation. Verify it in the release pipeline and include newly added release files. An unsigned manifest is an integrity aid, not independent proof of publisher identity.

## F10 — Cloud retention is request-driven

**Location:** `cloud/server.py`, lines 36–48 and 62–63.

Reports get an expiry timestamp 24 hours after upload. Expired rows are deleted only inside `authorized()` when a subsequent authorized request reaches cleanup. There is no startup or periodic sweep. A quiet server can therefore retain expired reports on disk beyond 24 hours, even while running. A later authorized read will trigger cleanup before returning data; this finding concerns stored retention, not successful retrieval of an expired report.

**Fix:** add bounded startup/periodic expiry maintenance and document how stopped servers, exports and backups affect physical retention. Test idle expiry without making another API request.

## What is working

- Server-side session consent validation and scope-specific checks.
- Loopback WebSocket binding, exact browser origins, token comparison and rejection of a second controller.
- Normal disconnect/heartbeat cleanup with responsive test detectors.
- Parameterized SQLite queries, foreign-key deletion and secure-delete configuration.
- Persisted Ed25519 checkpoints and chained events; tests reject edited, reordered, truncated and rehashed data, and the wrong independently pinned key.
- Cloud uploads require explicit approval and enrolled public keys; read credentials cannot upload or delete.
- Candidate notes are escaped in the main dashboard and PDF text.
- Gaze does not affect the technical index, and documentation explicitly rejects automatic hiring conclusions.

These controls have value, but signatures cannot establish observation completeness or trust in a candidate-controlled endpoint. The project already documents that distinction; it is not counted as a newly discovered defect.

## Packaging and release gaps

The ZIP is 152,457,595 bytes, approximately 145.4 MiB. Its bundled Windows Python environment alone accounts for 415,361,169 uncompressed bytes, approximately 396.1 MiB. It also contains test databases and three 32-byte signing-key fixture files under `scratch/test_*`. Their placement suggests test fixtures; this review does not establish that any production identity is exposed. Exclude generated environments, development databases and signing-key files from distributable source archives. If any included key was enrolled elsewhere, retire that identity.

The Tauri resource configuration bundles worker source and SQL, but no portable Python runtime. The sidecar staging script is a development helper and its own release guide requires additional resource configuration. A source archive containing a developer's environment is not a portable installer. The README already acknowledges this limitation, so it is treated as an unfinished release requirement rather than a hidden capability claim.

The dependency graph is not fully locked for reproducible desktop builds. Clean Windows/macOS installs, exact pinned dependency tests, native permission and forced-shutdown checks, signing/notarization and real hardware validation remain necessary. Detection false-positive/false-negative rates have not been established; the index and confidence percentages are heuristics.

## Recommended order of work

1. Fix F01–F03 and add lifecycle/evidence regression tests before any real-candidate use.
2. Resolve F04–F07, align disclosures, and label report generation accurately.
3. Repair the browser test, refresh release hashes, and make cloud expiry independent of traffic if cloud reporting is used.
4. Produce clean release artifacts and verify the exact dependency pins on Windows and macOS. Exercise allow/deny/delayed permissions, camera contention, disconnects, blocked probes, normal stop and forced exit.
5. Treat technical observations as review material only. Any later claim of detection effectiveness needs a separately designed and measured evaluation.

The application has a useful prototype foundation. The next development effort should prioritize reliable stopping, accurate disclosure and complete evidence before adding more detection features.
